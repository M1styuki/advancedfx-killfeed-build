# Seven-map storm behavior and validation

The controller extends the existing Dust2, Mirage, Cache, Inferno, Ancient, Nuke and Anubis weather profiles. Existing rain, wet-ground and contact data are unchanged. It preserves the selected mirv_sky material and adds adjustable sunlight reduction, sun-card suppression, scene exposure, grading, an authored lightning bolt, transient illumination, rain audio and thunder.

## Lightning semantics

Kill-triggered lightning requires at least one mirv_deathmsg filter rule. With no filters, no kill triggers lightning, even if deathmsg debug, lifetime or highlighting is configured. With configured filters, only the final nonblocked real, non-self kill triggers. The notification belongs exclusively to the right-top killfeed handler after the complete filter and block decision; the POV DeathPanel does not notify weather. The xTrace rule resolves its player when the rule is added. No camera re-trace is introduced.

Demo-time lightning is independent of the filter list. The demo/kills/both/off modes select event sources. Pausing, disabling, changing maps and seeking clear owned transient particles, delayed thunder and pending kill events. Multiple accepted kills in one render-frame batch share a single bounded flash/thunder burst; the accepted-kill counter records each kill. The `paused` field in the status line is the demo pause state of the last weather frame, so a `rainAudio`/`thunderAudio` of 0 while paused is expected rather than a failure.

Each accepted event places the authored bolt's control points so an ordinary horizontal first-person sky view actually intersects part of the strike: the endpoint is about 1600 units forward and about 320 units above the camera, and the start is about 1050 units above the endpoint, instead of the previous placement in which almost the whole bolt sat above the visible sky. Native depth testing still keeps the strike behind buildings.

## Rendering and audio ownership

Grading uses a private deferred D3D11 context and executes with context-state restoration. It preserves predication, avoids duplicate processing of the same target in one presented frame, and excludes the entire POV death-fade window and active player flash. HUD is drawn later. BeforeUi stream capture and ReShade input include the grade, so additional ReShade grading can compound the appearance. Owned draws bypass HLAE's color/depth blockers and must be included in recording acceptance.

Multisampled scene colour is supported instead of being rejected. When the current target is MSAA (2x/4x/8x and the MSAA view dimension), the pass first resolves the multisampled target into an owned single-sample colour texture, samples that texture in the fullscreen pass, and still draws back into the original multisampled render target. The single-sample texture is created with the typed resource format (an RTV view format is always typed, so a typeless resource resolves through its view format), its shader-resource view is created with the typed view format, and the resolve only runs when the device reports multisample-resolve support for the format. Only a single-array-slice, single-mip, single-sample-resolution target is accepted; other view dimensions, formats, arrays, mips and sample counts are refused. The previous native depth/stencil state, blend state, viewport binding and predication are untouched: the copy/resolve happens on the immediate context with predication cleared for the resolve/copy/execute window and restored afterwards, and the owned record is executed with command-list state restoration. There is deliberately no after-HUD fallback, so a refused target loses grading rather than being drawn at the wrong point in the frame. A refusal is latched per target signature so the same unsupported target is diagnosed once instead of every presented frame; counters show whether the target was reached, which sample count and formats were seen, the last refusal reason and any resolve/draw error. These counters prove only that the pass was attempted, never that the result is visible.

Native scalar overrides are restored only for matching entity identities and values still owned by this controller. Audio playback tracks only its own instances and never issues global stopsound. Rain is a stereo ambient loop, without roof-aware indoor/outdoor routing. Turning both audio effects off stops the instances before releasing their definition references; reload or map reset allows a failed definition lookup to retry. Particle, illumination and thunder switches remain independent.

Storm audio does not latch a failed native initialization for the rest of the process, and it no longer depends on the POV sound-circle. Weather resolves and validates its own owned sound interface through `MirvPovSoundCircle_InitializeOwnedAudio`: the unique direct start helper, the sound-event interface global reached from that helper's validated tail, the unique stop wrapper (with its validated callee prefix) and the owned system singleton. It installs no radar, local-pawn or network sound hook, and a failed POV initialization cannot clear or gate it. Initialization is only considered complete once the owned start helper, event interface, stop helper and system slot are all present; until then it is retried at a bounded, backing-off cadence (a few seconds, capped), so a transiently unavailable interface can still come up later without a per-frame cost. Readiness fails closed when any native pattern or instruction tail no longer matches. Status reports structured owned readiness (owned/start/stop/system/event-interface), the number of initialization attempts, the most recent owned-sound failure stage (init, start, stop, system, event-interface, name validity or GUID), and per-rain/per-thunder attempt and success counts. The registered-event stages are computed independently of whether a playback GUID is currently active or the demo is paused, and they are reported separately from retained sound definitions. No native function address, pattern or ABI was changed for this.

Particle spawn diagnostics report, per owned particle resource, the attempt count, definition-load failures, create failures, created count, live count and a short failure stage, plus the early-return reason for the spawn as a whole (requested/profile/config/layout/native-interface/resource-system/manager/time). Rain reports the same counters for its host-creation path. These are submission counters and do not prove visible output; they exist so a missing definition can be told apart from a missing manager or a rejected create. They are printed only by the status command, never per frame, and never print addresses.

The seven new effects each have an immediate Release mirv_pov_debug_feature control. Weather does not require mirv_pov. Weather resolves its own owned sound interface and never installs the POV soundcircle hooks, so the independently gated POV behavior is unaffected. The guide lists commands and defaults.

## Diagnostic manual test

`mirv_weather lightning test` is a diagnostic-only request. It is queued and consumed on the next normal weather frame that is active and unpaused; while paused it stays queued, and a seek, map change, storm reset or disabling the storm layer drops it. It invokes one complete lightning feedback event (particle attempt, flash and delayed thunder) independently of the demo-time schedule and of the kill-filter mode, and it has its own counter, so it can never be mistaken for an automatic demo event or a retained kill. It does not fabricate a kill event, does not bypass the resource/ownership guards, and does not change the selected sky. It follows the existing `weather_lightning`, `weather_lightning_light` and `weather_thunder` feature switches; if all three are off the queued request is reported as ignored. A manual test that fires does not imply that automatic kill triggers were exercised.

## Diagnostic visible-rope control probe

`mirv_weather lightning probe` is a separate confirmation tool, distinct from `mirv_weather lightning test`. It references the installed native `particles/impact_fx/impact_wallbang_light_silent.vpcf` control effect by name only (no asset bytes and no copied game data) and drives it through the same already-validated owned particle interfaces as the authored bolt: manager lookup, resource precache with a retained definition binding, create with the same attachment argument, manager/record identity matching, then the CP0/CP1 update. Both control points stay inside that control's native 1000-unit draw distance: CP0 is 450/525/600 units ahead of the camera and 40/60/80 units above it, and CP1 is 250/275/300 units above CP0.

It queues three bounded pulses spaced 0.75 demo seconds apart, the first 1.5 demo seconds after the command, so the console can be closed before the short effect appears. It requires the supported, enabled, unpaused weather layer and a normal render frame. It is deliberately independent of the `weather_lightning`, `weather_lightning_light` and `weather_thunder` switches, of the demo/kill schedule and of the kill-filter list, so it can confirm the native particle path even when the authored bolt is gated off. It creates no flash, no kill event and no thunder, and it never spawns the authored bolt or the native cloud. Resources are bounded (three pulses, at most four live control particles, 1.5 demo seconds each); pause, seek, map change, storm off, weather master off or shutdown drops the pending sequence and destroys owned probe particles synchronously together with their retained bindings.

Status reports the probe separately from the authored bolt/cloud and from the manual test: queued, dropped, pending, remaining, fired, definition failures, create/record failures, created, live and the stage name (including `queued`, `paused` and `dropped`). As with every other submission counter, a created/live count only proves that the native create/update path was reached; it does not prove that a line is visible. This is the discrimination step: if the control renders and the authored bolt does not, the authored definition is the suspect; if the control also does not render, the runtime control-point/visibility/pass path is the suspect. Actual visibility remains a user observation.

## Validation boundary

Independent review identified rendering-state, transient-cleanup and death-fade defects; the fix round isolates drawing, adds synchronous cleanup, and guards the fade transition. The user's explicit no-filter/no-kill-lightning requirement is authoritative. Local static review and whitespace checks are followed by cloud Windows Release x64 and exact embedded HLSL VS/PS compilation. Downloaded DLL/source correspondence and installed-file checks are required before delivery.

Compilation, review and counters do not establish visible or audible success. In-game seven-map indoor/outdoor lighting, lightning, actual audio, filtered-kill behavior, repeated seeks, pause/restore, full-white flash, death fades, HUD and recording remain acceptance items. Existing baked lightmaps/reflections are not rebuilt. Detailed native investigation records remain local rather than being included in the public diagnostic corpus.

## Authored storm bolt

The installed game data has `m_bDisableOperator=true` on the shipped `storm_lightning_01_thin` and `branch_01/02/03` rope renderers, and the remaining native cloud renderer is a dark-smoke flash rather than a visible bolt; the photo resources override their endpoints to a tiny preset and carry unrelated spark/light children, so they are not weather bolts either. The controller therefore drives its own authored bolt:

* Runtime path `particles/mirv_weather/storm_bolt.vpcf`, installed as `resources/AfxHookSource2/cs2/particles/mirv_weather/storm_bolt.vpcf_c`. The native cloud `particles/rain_fx/storm_lightning_01_cloud.vpcf` is kept only as an optional secondary flash; the disabled thin/branch resources are no longer spawned. No additional rain instance is created.
* The resource is an original, minimal definition (no Valve asset copy): one enabled `C_OP_RenderRopes` that references the installed `materials/particle/bendibeam.vtex` by name, a `C_INIT_CreateSequentialPath` of 32 points from CP0 to CP1, independently authored +/-24 XY and +/-3 Z jitter, a cool-white constant colour, radius 4..6, alpha 1, an instantaneous 32-particle emitter, and decay/fade-out. The runtime sets CP0/CP1 immediately after creation, exactly as it did for the previous native resources.
* `tools/generate_weather_bolt.py` is the complete corresponding source. It uses only the standard library, is byte-for-byte deterministic, and writes an uncompressed Source 2 KV3 v3 DATA block plus the RERL external reference for the texture. CI runs it and copies the result into the weather package, so no compiled asset is checked in.
* The generator re-reads its own output with an independent decoder and fails if any pool, alignment, string index, resource flag, external-reference hash or authored property is wrong. The generated runtime resource is included in the package; decoded native investigation data remains private and temporary.
* Status still separates the authored bolt (`bolt`) from the optional native cloud (`cloud`) with the per-resource counters, so an authored definition/create failure cannot be hidden by a successful cloud spawn. The extra bolt resource leaves the existing 47 weather resources untouched.

The authored bolt has been structurally decoded and hash-checked locally; whether it is visible in game, and whether the shipped placement reads well, remain in-game acceptance items.
